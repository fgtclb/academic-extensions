The active filters of a project list, as tags, and the link that resets them. Every category tag links to the list with its category removed, every other category, the active state and the sorting kept. An active state other than "all" is a tag as well, which links to the list with the state "all" and keeps the categories. A link always carries the sorting and the active state, which still counts as a selection: only a request without any demand argument applies what the content element presets, so the visitor does not get back a preset they removed. The category tags follow the category filter, the state tag follows the state select: a tag is shown only while the visitor can change what it removes. The category tags follow the type order of the category group, the order of the filters. The loop reads `allCategoriesByType` rather than the category collection itself: the collection is an iterator with a single position, and `ct:filterArgument` walks the same collection inside the loop, which would end the loop after the first tag. The reset link leads to the page without any argument, so the list shows what the content element presets. It is offered while the list shows a visitor's selection, `visitorSelection`, and a category or an active state other than "all" is selected or preset by the content element, also once the visitor removed the preset. On the bare page it would lead to what is already shown, and with nothing selected and nothing preset it would reset nothing but the sorting. Only categories of the types the collection was built for get a tag, which are all of them for the collections the demand factory builds. A collection a demand listener builds by hand without type identifiers gets no tags. Arguments: the "SortingAndFilters" partial renders it with "{_all}". - demand: the demand of the list shown - settings: for `hideFilter`, `hideActiveState`, `filter.showActiveFilters` and `filter.showReset` - visitorSelection: whether the request carried a demand
